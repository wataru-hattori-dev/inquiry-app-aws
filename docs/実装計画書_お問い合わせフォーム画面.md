画面要件定義書「11. 不明点リスト」および実装上の隙間。

| ID | 内容 | Plan 仮置き（仕様確定ではない） |
|----|------|----------------------------------|
| U-01 | 成功後の画面遷移 | 同一画面残留 + 成功メッセージ。一覧への自動遷移はしない |
| U-02 | 環境変数名 | `VITE_API_BASE_URL`（末尾スラッシュはクライアントで正規化） |
| U-03 | 文字数カウンタ | **実装しない**（必須ではない） |
| U-04 | 成功メッセージ自動消去 | **実装しない**（次の送信結果で上書き）。手動クリア不要 |
| P-01 | 送信時 trim | Body 送信前に各フィールドを `trim()` して送る（空チェックも trim 後）。長さは trim 後文字列で判定してサーバー超過を減らす |
| P-02 | メール regex | サーバーと同等: `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`（`create_inquiry.py` の `EMAIL_PATTERN`） |
| P-03 | 送信中の入力欄 | **disabled にする**（画面要件 B-06 推奨を採用） |
| P-04 | 成功メッセージ文言 | 「お問い合わせを受け付けました」 |
| P-05 | 500 / 通信失敗文言 | 画面要件 6.3 の例文をそのまま使用 |
| P-06 | API 未起動時の確認方式 | 方式は固定しない。合格条件は「ブラウザ Origin から OPTIONS+POST が CORS 許可されること」。推奨はデプロイ済み `ApiEndpoint`。SAM local を使う場合は CORS が同等であることを確認 |
| P-07 | `frontend/` と一覧の同居 | 今回はフォームのみマウント。一覧コンポーネントは作らない（後続 Phase 用のディレクトリ予約もしない） |

**要 Spec 更新になり得る事項（本 Plan では変更しない）**

| 事項 | 現状 | 扱い |
|------|------|------|
| サーバーが trim せず永続化 | `create_inquiry` は空チェックに `strip` を使うが、保存値は trim 前 | FE 側で trim して送ることで回避。サーバー側 trim 統一は任意の改善 → やるなら **要 Spec / 実装更新** |
| `name` 長さが trim 前で判定 | サーバーは `len(name)`（未 trim） | FE は trim 後で長さ判定。不一致を避けるため送信は trim 済みのみ |

## 3. 画面・コンポーネント構成

### 3.1 画面イメージ（責務）

単一ルート（`/`）に投稿フォームのみ。

```
App
 └─ InquiryForm
      ├─ フィールド: name / email / message（label 対応）
      ├─ フィールドエラー表示（各入力近傍）
      ├─ フォーム全体メッセージ（成功 / API・通信エラー）
      └─ 送信ボタン（ローディング・disabled）
```

### 3.2 実装単位（ファイル想定）

| パス（想定） | 責務 |
|--------------|------|
| `frontend/`（Vite 生成一式） | プロジェクト骨格。不要デモは削除または置換 |
| `frontend/src/types/inquiry.ts` | `CreateInquiryRequest` / `Inquiry` / `ApiError` |
| `frontend/src/lib/validation.ts` | クライアントバリデーション（規則の単一箇所） |
| `frontend/src/api/client.ts` | ベース URL 取得・正規化、`createInquiry`、エラー解釈 |
| `frontend/src/components/InquiryForm.tsx` | フォーム状態・送信フロー・UI |
| `frontend/src/App.tsx` | InquiryForm をマウント |
| `frontend/src/main.tsx` / `index.html` | エントリ |
| `frontend/.env.example` | `VITE_API_BASE_URL=` の例（コミット可） |
| `frontend/.env` または `.env.local` | 実 URL（**コミット禁止**） |
| `frontend/src/vite-env.d.ts` | `ImportMetaEnv` に `VITE_API_BASE_URL` を宣言 |

疑似コードは置かない。状態の最小セット:

- 入力値: `name`, `email`, `message`
- `fieldErrors`: フィールド単位
- `formMessage`: `{ type: 'success' \| 'error'; text: string } \| null`
- `isSubmitting`: boolean

### 3.3 責務境界

- **validation**: API を呼ばない。成功時は trim 済み payload を返す
- **api/client**: UI 状態を持たない。`201` → Inquiry、それ以外は ApiError または通信エラーに正規化
- **InquiryForm**: バリデーション → 送信中 UI → API → メッセージ。一覧再取得はしない

## 4. 環境変数とローカル起動方針

| 項目 | 方針 |
|------|------|
| 変数名 | `VITE_API_BASE_URL` |
| 値の例 | `https://{api-id}.execute-api.{region}.amazonaws.com`（SAM Output `ApiEndpoint`） |
| 正規化 | 末尾 `/` を除去してから `/inquiries` を連結 |
| 未設定 | アプリ表示時または送信直前に明確なエラー（例: 「API の URL が設定されていません」）。曖昧な `Failed to fetch` だけにしない |
| 起動 | `cd frontend && npm install && npm run dev`（例: `http://localhost:5173`） |
| API | デプロイ済み推奨。ローカル API を使う場合も CORS がブラウザ Origin を許可していること |

## 5. API 連携・型・メッセージ

### 5.1 契約（変更しない）

| 項目 | 内容 |
|------|------|
| Method / Path | `POST /inquiries` |
| Headers | `Content-Type: application/json` のみ（Authorization 付与禁止） |
| Body | `{ name, email, message }`（trim 済み） |
| 成功 | `201` + Inquiry（`id`, `created_at`, `name`, `email`, `message`） |
| 失敗 | `400`/`500` + `{ error, message }`（`common.py` により CORS ヘッダ付き） |

### 5.2 型（名称は実装で可）

- `CreateInquiryRequest`: `{ name: string; email: string; message: string }`
- `Inquiry`: 上記 + `id: string; created_at: string`
- `ApiError`: `{ error: string; message: string }`

`any` 禁止。レスポンス JSON は型ガードまたは安全な狭義化で扱う。

### 5.3 成功 / エラー表示

| 結果 | 表示 |
|------|------|
| `201` | 成功メッセージ（P-04）。入力クリア。フィールド/API エラー消去。`id`/`created_at` の表示は任意（必須ではない → 本 Plan では出さない） |
| `400 ValidationError` | フォーム上部に API `message`（英語のまま可。フィールドマッピングは初期はしない） |
| `500` | 汎用文（画面要件の例） |
| ネットワーク / CORS / 想定外 | 「サーバーに接続できませんでした」等 |
| 成功とエラー | 同時表示しない（新しい結果で上書き） |

送信完了後は必ず `isSubmitting = false`。

## 6. クライアントバリデーションと送信中 UI

### 6.1 バリデーション（送信前・失敗時 API 未呼び出し）

| フィールド | 規則（サーバー整合） | メッセージ例 |
|------------|----------------------|--------------|
| name | trim 後非空、最大 100 | 画面要件 4.2 の日本語例 |
| email | trim 後非空、最大 254、P-02 の regex | 同左 |
| message | trim 後非空、最大 2000 | 同左 |

長さは **trim 後** の文字列長で判定（仮置き P-01）。

### 6.2 送信フロー（B-01〜B-08 / FE-01〜FE-07）

1. submit（`preventDefault`）
2. クライアントバリデーション → 失敗ならフィールドエラー表示して終了
3. `isSubmitting = true`（ボタン disabled、ローディング表示、入力 disabled、`aria-busy` 推奨）
4. `POST` 実行
5. 成功/失敗でメッセージ更新
6. 必ず送信中解除

二重送信防止は disabled で担保。ページリロード submit は行わない。

## 7. CORS / ローカル動作確認手順

### 7.1 前提（インフラ・BE — 変更しない）

`template.yaml`: Methods GET/POST/DELETE/OPTIONS、Headers Content-Type/Authorization、Origins `*`。  
Lambda: 成功・失敗とも `Access-Control-Allow-Origin: *`（`common.py`）。

### 7.2 確認手順（合格条件）

1. API ベース URL を `.env.local` 等に設定（コミットしない）
2. `npm run dev` で Vite を起動
3. ブラウザでフォームを開き、開発者ツール Network を開く
4. 正常入力で送信
5. **OPTIONS**（プリフライト）が成功系であること
6. **POST** `/inquiries` が `201` であること
7. 画面に成功メッセージが出てフォームがクリアされること
8. 異常系: 空送信（API が Network に出ない）、可能なら API 側 400/500 または DevTools で Offline 相当

フロントは独自禁止ヘッダーを付けない。
