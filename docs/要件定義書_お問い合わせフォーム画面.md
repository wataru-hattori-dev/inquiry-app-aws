## 1. 機能概要 / 目的

利用者がブラウザ上で氏名・メール・本文を入力し、問い合わせを新規登録できる画面を提供する。  
送信はフロントから API Gateway 経由で `POST /inquiries` を呼び、成功・失敗を画面上で分かるようにする。

---

## 2. 前提・対象外

### 2.1 前提

- フロントエンドは React + TypeScript（Vite）。
- API ベース URL は `import.meta.env`（`.env`）経由で参照する。
- TypeScript で Inquiry / エラー型を定義し、`any` を多用しない。
- サーバー側バリデーション（`docs/spec.md` 3.3）と矛盾しないクライアント側チェックを行う。
- `id` / `created_at` はクライアントが送らず、サーバーが生成する（送ってもサーバーが無視する前提。フォームからは含めない）。
- API は初期スコープで認証なし（公開）。Authorization ヘッダーは本画面では付与しない。

### 2.2 対象外（本画面 Spec）

- 一覧表示・削除 UI（管理画面。別 Spec / `spec.md` 6 の管理画面）
- 問い合わせの更新・詳細取得
- メール通知
- 本番向け CORS Origin 制限（開発時は Origin `*`）
- ビジュアルデザインの詳細（カラー・レイアウトのデザインシステム）

---

## 3. ユースケース（正常系）

### UC-F01 問い合わせを送信する

1. 利用者がフォームを開く。
2. `name` / `email` / `message` を入力する。
3. 送信ボタンを押す。
4. クライアント側バリデーションが成功する。
5. 送信中はローディング表示し、再送信できない状態にする。
6. フロントが `POST /inquiries` に JSON を送る。
7. API が `201` と作成済み Inquiry を返す。
8. 画面に成功メッセージを表示し、入力内容をクリアする（または送信完了状態にする）。

---

## 4. 入力フォームの構成とバリデーション（①）

### 4.1 フィールド構成

| フィールド | UI | 必須 | 送信キー | 備考 |
|------------|-----|------|----------|------|
| 名前 | テキスト入力（1 行） | Yes | `name` | 問い合わせ者名 |
| メール | テキスト入力（`type="email"` 推奨） | Yes | `email` | 連絡先 |
| 本文 | 複数行テキスト（textarea） | Yes | `message` | 問い合わせ本文 |
| 送信 | ボタン | — | — | ラベル例: 「送信」 |

フォームは上記 3 入力 + 送信ボタンを最低限含む。  
`id` / `created_at` 用の入力欄は設けない。

### 4.2 クライアント側バリデーション規則

`docs/spec.md` 3.3 に合わせる。送信前に検証し、失敗時は API を呼ばない。

| フィールド | 規則 | 表示メッセージ例（日本語可） |
|------------|------|------------------------------|
| `name` | 必須。trim 後が空でないこと。最大 100 文字 | 「名前を入力してください」「名前は 100 文字以内で入力してください」 |
| `email` | 必須。trim 後が空でないこと。最大 254 文字。簡易メール形式（`local@domain`。実装上はサーバーと同等のパターンを推奨） | 「メールアドレスを入力してください」「メールアドレスの形式が正しくありません」 |
| `message` | 必須。trim 後が空でないこと。最大 2000 文字 | 「お問い合わせ内容を入力してください」「本文は 2000 文字以内で入力してください」 |

補足:

- 文字数は入力文字列の長さで判定する（`name` / `message` は trim 後の空チェックと、長さチェックを行う。長さ上限は `spec.md` の「最大 N 文字」に従う）。
- フィールドエラーは該当入力の近傍に表示する。
- サーバーが返す `400 ValidationError` とも整合するよう、規則をサーバーと揃える。

### 4.3 型（要件）

少なくとも次を TypeScript で表現する（名称は実装で可）。

- 作成リクエスト: `{ name: string; email: string; message: string }`
- 作成成功レスポンス（Inquiry）: `{ id: string; created_at: string; name: string; email: string; message: string }`
- API エラー: `{ error: string; message: string }`

## 5. 送信ボタン押下時の挙動（②）

| ID | 要件 |
|----|------|
| B-01 | 送信クリック（または form submit）でクライアントバリデーションを実行する |
| B-02 | バリデーション失敗時は API を呼ばず、フィールドエラーを表示する。送信ボタンは再び押せる |
| B-03 | バリデーション成功後、リクエスト開始から完了（成功/失敗）まで **送信中状態** とする |
| B-04 | 送信中はローディング表示を行う（ボタン文言変更、スピナー、aria-busy 等のいずれか以上） |
| B-05 | 送信中は送信ボタンを disabled にし、連打・二重送信を防ぐ |
| B-06 | 送信中は入力欄を編集不可（disabled / readOnly）にしてもよい（推奨）。少なくとも再 submit は不可 |
| B-07 | リクエスト完了後は送信中状態を解除する（成功後にフォームをクリアする場合も、解除後の状態を明確にする） |
| B-08 | ブラウザのデフォルト submit によるページリロードは行わない（SPA として防ぐ） |

## 6. API 接続・レスポンス処理（③）

### 6.1 リクエスト

| 項目 | 内容 |
|------|------|
| Method | `POST` |
| URL | `{VITE_API_BASE_URL}/inquiries`（環境変数名は `.env` で定義。ベース URL 末尾スラッシュ有無は実装で正規化） |
| Headers | `Content-Type: application/json` |
| Body | `{ "name", "email", "message" }`（画面入力値。必要なら trim して送る） |

### 6.2 成功時（`201 Created`）

| 項目 | 要件 |
|------|------|
| 判定 | HTTP ステータス `201`、ボディを Inquiry 型として扱う |
| 表示 | 成功メッセージを表示する（例: 「お問い合わせを受け付けました」） |
| フォーム | 入力値をクリアする |
| エラー表示 | 直前のフィールド／API エラー表示をクリアする |
| 備考 | 返却の `id` / `created_at` を画面に出してもよいが、必須ではない |

### 6.3 エラー時

| 状況 | 要件 |
|------|------|
| `400` + `error: ValidationError` | API の `message` をユーザー向けに表示する（フィールド特定できなければフォーム上部の汎用エラー領域） |
| `500` + `error: InternalServerError` | 汎用メッセージを表示する（例: 「送信に失敗しました。時間をおいて再度お試しください」）。`message` を補助表示してもよい |
| ネットワークエラー / CORS 失敗 / 応答不能 | 通信失敗として汎用エラーを表示する（例: 「サーバーに接続できませんでした」） |
| JSON 不正・想定外ステータス | 汎用エラーを表示する |
| 型 | レスポンスの `error` / `message` を型定義して利用する（`spec.md` 5.3-4） |

エラー表示中に利用者が再編集・再送信できること。送信中状態は必ず解除する。

### 6.4 メッセージ表示領域

画面上に少なくとも次を区別できること。

1. フィールド単位のバリデーションエラー  
2. API / 通信のエラー（フォーム全体）  
3. 成功メッセージ  

成功とエラーは同時に出さない（新しい結果で上書き）。

## 7. CORS・ローカル動作確認要件（④）

### 7.1 CORS（フロントが依存する前提）

開発時、API 側は次を満たしていること（`template.yaml` / `spec.md`）。

| 項目 | 値 |
|------|-----|
| AllowMethods | `GET`, `POST`, `DELETE`, `OPTIONS` |
| AllowHeaders | `Content-Type`, `Authorization` |
| AllowOrigins | `*` |
| Lambda 応答 | 成功・失敗の双方に `Access-Control-Allow-Origin` 等の適切な CORS ヘッダー |

本画面の `POST` はプリフライト（`OPTIONS`）後に `Content-Type: application/json` で送る想定。  
フロント実装で独自の禁止ヘッダーを付けてプリフライトを壊さないこと。

### 7.2 ローカル動作確認に必要な要件

| ID | 要件 |
|----|------|
| L-01 | Vite 開発サーバー（例: `http://localhost:5173`）から、デプロイ済み（または同等の）API へ `POST /inquiries` できること |
| L-02 | `.env`（例: `.env.local`）に API ベース URL を設定できること。リポジトリにシークレットをコミットしない |
| L-03 | 環境変数未設定時は、送信前または起動時に分かるエラー／警告とし、曖昧な失敗にしない |
| L-04 | ブラウザ開発者ツールで、プリフライト `OPTIONS` と本リクエスト `POST` が 成功系で通ることを確認できること |
| L-05 | 正常系: バリデーション OK → `201` → 成功メッセージ → フォームクリア |
| L-06 | 異常系: クライアントバリデーション、API `400`、API `500`（または模擬）、ネットワーク切断相当をそれぞれ確認できること |

ローカルで API まで立てる方式（SAM local 等）は本 Spec では方式を固定しない。いずれの場合も **ブラウザ Origin と API の CORS が許可されること** を動作確認の合格条件とする。

## 8. 例外・分岐まとめ

| 分岐 | 期待 |
|------|------|
| 未入力・空白のみ・文字数超過・メール形式不正 | API 未呼び出し。フィールドエラー表示 |
| 送信中の再クリック | 無視（ボタン disabled） |
| `201` | 成功メッセージ + フォームクリア |
| `400 ValidationError` | API `message` を表示。再入力可 |
| `500` / 通信失敗 / その他 | 汎用エラー表示。再送可 |
| ページリロード submit | 発生させない |

## 9. 非機能（画面）

| ID | 内容 |
|----|------|
| NF-F01 | 二重送信防止（送信中 disabled） |
| NF-F02 | 送信中のフィードバック（ローディング） |
| NF-F03 | 設定は `.env` 経由 |
| NF-F04 | 型安全（Inquiry / ApiError） |
| NF-F05 | アクセシビリティ最低限: ラベルと入力の対応、送信中は `disabled` / 必要なら `aria-busy` |

## 10. テスト観点（概要）

| ID | 観点 |
|----|------|
| TF-01 | 3 フィールド表示と送信ボタンがある |
| TF-02 | 空送信で API が呼ばれずエラー表示される |
| TF-03 | 各フィールドの最大長・メール形式で弾かれる |
| TF-04 | 送信中はボタンが押せない／ローディングが見える |
| TF-05 | 成功時 `201` 相当で成功メッセージとクリア |
| TF-06 | `400` / `500` / ネットワークエラーでメッセージが出る |
| TF-07 | localhost から実 API（または同等）へ CORS 込みで POST できる |
| TF-08 | API URL が env から読まれる |
