## 1. 揺れ・不足の検出結果と仮置き方針

要件定義書「11. 不明点リスト」への本 Plan での仮置き。Build 中に変更する場合は、先に要件定義書を更新してから実装する。

| ID | 論点 | 仮置き方針（Plan 確定） |
|----|------|-------------------------|
| Q1 | 必須フィールド | `name` / `email` / `message` の 3 つを必須とする。他フィールドは初期スコープでは受け取っても永続化しない |
| Q2 | バリデーション | `name`: 必須・空/空白のみ不可・最大 100 文字。`email`: 必須・簡易形式（`local@domain`）・最大 254 文字。`message`: 必須・空/空白のみ不可・最大 2000 文字 |
| Q3 | DELETE 成功 | `204 No Content`（ボディなし）に統一 |
| Q4 | GET 形状 | `{ "items": [ ... ] }`。0 件は `{ "items": [] }`。※要件の「配列」は `items` 内の配列として解釈 |
| Q5 | 並び順 | `created_at` 降順。サーバー側（Lambda）でソート |
| Q6 | id / created_at 生成 | `id` は UUID v4 文字列。`created_at` は ISO 8601・タイムゾーン付き。実装は `Asia/Tokyo`（`+09:00`）で統一 |
| Q7 | クライアント送信の id / created_at | 無視してサーバー採番（エラーにしない） |
| Q8 | 認証 | 初期リリースは完全公開 API。`Authorization` は CORS 将来用のみ |
| Q9 | 画面構成 | 単一画面。上部フォーム＋下部一覧。削除前にブラウザ確認ダイアログ。成功/失敗は画面上のメッセージ領域に表示 |
| Q10 | FE デプロイ | 初期スコープはローカル開発サーバのみ。ホスティング IaC は作らない |
| Q11 | spec.md 関係 | 本計画完了後も `docs/要件定義書.md` を正とする。`spec.md` / `plan.md` は廃棄せず参考残置。追随更新は任意・非必須 |

### 1.1 追加の実装上の仮置き

| 項目 | 仮置き |
|------|--------|
| 共通レスポンスヘッダ | 成功・失敗とも `Access-Control-Allow-Origin: *`。JSON ボディがある場合は `Content-Type: application/json` |
| DELETE 存在確認 | `DeleteItem` で `ReturnValues=ALL_OLD` 等により削除前アイテム有無を判定。無ければ `404 NotFound` |
| DELETE `id` 欠落 | パス `id` が空・未指定なら `400 ValidationError` |
| 不正 JSON | `400 ValidationError` |
| 一覧取得手段 | DynamoDB `Scan`（初期スコープ・ページネーションなし） |
| FE 環境変数名 | `VITE_API_ENDPOINT`（末尾スラッシュ有無はクライアント側で正規化） |
| バックエンド共通処理 | `backend/src/common.py`（または同等）に CORS・エラー JSON・テーブル名取得を集約してよい |
| pytest | 必須ではない。最低限は `sam local` / curl / ブラウザ手動 |

## 3. ファイルごとの実装方針・責務境界

コード本体は書かない。責務のみ定義する。

### 3.1 インフラ

#### `template.yaml`

- **責務**: DynamoDB / HTTP API / 3 Lambda / IAM / CORS / Output `ApiEndpoint` の定義
- **境界**: ビジネスロジックを持たない。ハンドラ名・CodeUri・権限が本計画のソース配置と一致していること
- **確認観点**: Create=Write / List=Read / Delete=`DeleteItem` のみ。Methods に DELETE を含む CORS

### 3.2 バックエンド

#### `backend/requirements.txt`

- **責務**: SAM ビルドで解決する Python 依存の宣言
- **境界**: アプリケーションロジックを書かない

#### `backend/src/common.py`（推奨）

- **責務**: 共通 CORS ヘッダ、`{error,message}` 生成、成功レスポンスヘルパ、`TABLE_NAME` 読み込み
- **境界**: DynamoDB の業務操作（Put/Scan/Delete）は各ハンドラに残す。個人情報をログ出力しない

#### `backend/src/create_inquiry.py`

- **責務**: Body パース → バリデーション → `id`/`created_at` 付与 → PutItem → `201` + 作成オブジェクト
- **境界**: 一覧・削除ロジックを含めない。クライアントの `id`/`created_at` は無視

#### `backend/src/list_inquiries.py`

- **責務**: Scan → `created_at` 降順ソート → `200` + `{ "items": [...] }`
- **境界**: ページネーション・フィルタなし。書き込み・削除をしない

#### `backend/src/delete_inquiry.py`

- **責務**: パス `id` 検証 → DeleteItem（存在確認付き）→ 成功 `204` / 未検出 `404`
- **境界**: 一覧再取得はしない（クライアント側で GET する）

### 3.3 フロントエンド

#### `frontend/src/types/inquiry.ts`

- **責務**: API 契約に対応する型（Inquiry, CreateRequest, ListResponse, ApiError）
- **境界**: `any` 禁止。UI 文言やスタイルを持たない

#### `frontend/src/api/client.ts`

- **責務**: `VITE_API_ENDPOINT` 参照、3 API 呼び出し、非 2xx を ApiError として解釈
- **境界**: 画面状態（フォーム値・一覧キャッシュ）を持たない

#### `frontend/src/components/InquiryForm.tsx`

- **責務**: name/email/message 入力・送信・ローディング・成功/失敗表示。成功後に親へ通知（一覧再取得トリガ）
- **境界**: 一覧描画・削除を直接行わない

#### `frontend/src/components/InquiryList.tsx`

- **責務**: items 表示、削除確認ダイアログ、削除実行、親への再取得要求
- **境界**: 作成 API を呼ばない

#### `frontend/src/App.tsx`（および `main.tsx`）

- **責務**: 単一画面レイアウト、一覧取得の状態管理、子コンポーネント統合
- **境界**: fetch 詳細は `api/client` に委譲

#### `frontend/.env` / `.env.example`

- **責務**: API ベース URL の設定分離
- **境界**: シークレットを置かない（本 API は公開前提）

## 4. 処理フロー / 例外フロー（文章）

### 4.1 UC-01 作成（正常）

1. 利用者がフォームに name / email / message を入力し送信する。
2. フロントが `POST /inquiries` に JSON を送る。
3. Lambda が JSON をパースし、バリデーションを通す。
4. サーバーが UUID v4 の `id` と `+09:00` 付き ISO 8601 の `created_at` を付与し、DynamoDB に PutItem する。
5. `201` と作成オブジェクト（id, created_at, name, email, message）を CORS ヘッダ付きで返す。
6. フロントが成功メッセージを出し、一覧を再取得して表示する。

### 4.2 UC-01 作成（例外）

- Body が JSON として不正 → `400 ValidationError`
- 必須欠落・空白のみ・文字数超過・email 形式不正 → `400 ValidationError`（message に対象フィールドを示す）
- DynamoDB 障害・予期しない例外 → `500 InternalServerError`（共通 JSON + CORS）
- フロントは `message` を画面に表示し、一覧は更新しない（または直近の一覧を維持）

### 4.3 UC-02 一覧（正常）

1. 画面初期表示または再取得トリガでフロントが `GET /inquiries` を呼ぶ。
2. Lambda が Scan し、`created_at` 降順に並べ、`{ "items": [...] }` を `200` で返す。
3. フロントが一覧を描画する。0 件時は空状態を表示する。

### 4.4 UC-02 一覧（例外）

- 予期しない例外 → `500` + 共通 JSON
- フロントはエラーメッセージを表示する

### 4.5 UC-03 削除（正常）

1. 利用者が一覧の削除を選び、確認ダイアログで同意する。
2. フロントが `DELETE /inquiries/{id}` を呼ぶ。
3. Lambda が id を検証し、DeleteItem で削除。削除前アイテムがあれば `204`（ボディなし）。
4. フロントが一覧を再取得し、当該件が消えた状態を表示する。

### 4.6 UC-03 削除（例外）

- id 空・未指定 → `400 ValidationError`
- 対象なし → `404 NotFound`
- その他障害 → `500 InternalServerError`
- フロントはエラーを表示し、確認キャンセル時は API を呼ばない

### 4.7 CORS / OPTIONS

- ブラウザのプリフライトは API Gateway CORS 設定で処理する想定。
- Lambda の実レスポンスにも `Access-Control-Allow-Origin: *` を付与し、ブラウザからの GET/POST/DELETE を阻害しない。

要件定義書「9. テスト観点」を詳細化した一覧。ユニットと画面を区別する。

### 5.1 バックエンド（API / ローカル invoke・curl）

| ID | 観点 | 期待 |
|----|------|------|
| T-POST-01 | 正常作成 | `201`、body に `id` / `created_at` / 入力 3 項目 |
| T-POST-02 | email 欠落 | `400` `ValidationError` |
| T-POST-03 | 不正 JSON | `400` `ValidationError` |
| T-POST-04 | message 空文字 | `400` `ValidationError` |
| T-POST-05 | name/email/message 上限超過 | `400` `ValidationError` |

| T-GET-02 | 0 件 | `200`、`{ "items": [] }` |

| T-CORS-01 | ブラウザ DELETE 含む | CORS でブロックされない |
| T-IAM-01 | 権限レビュー | 各関数が要件の最小権限のみ |

| ID | 観点 | 期待 |
|----|------|------|

| T-UI-04 | API エラー | `message` が表示される |

| T-UI-06 | 型 | 主要経路で `any` を使っていない（レビュー） |

- 上記必須ケースが Pass
- エラーが常に共通 JSON
- 個人情報をログに出していない（コードレビュー）

- [ ] ホスティング IaC・認証は未実装のまま（スコープ外を守る）

## 7. リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| SimpleTable にソートキーなし | 時系列は Scan + アプリソート | 初期は許容。件数増は要件更新後に GSI 検討 |
| CORS Origin `*` / 公開 API | 誰でも一覧・削除可能 | 要件上スコープ外。必要時は要件定義書を先に更新 |
| `DynamoDBDeletePolicy` マネージド無し | デプロイ失敗 | 既存インライン `DeleteItem` を維持 |
| Scan のコスト・限界 | 大量データで遅延 | 初期非対象。ページネーションは要件追加後 |

## 8. Build フェーズへの引き渡しメモ

- 仕様の解釈に迷ったら **要件定義書 → 本計画の仮置き** の順で決める。
- `docs/spec.md` の詳細は本計画の仮置きと概ね整合するが、**正は要件定義書＋本計画**。
- デプロイや AWS リソース作成は、Build チャットでも利用者の明示許可がある Step のみ実行する。
- 1 回の Build 指示では、指定された Phase/Step 範囲だけを実装し、範囲外の先回り実装をしない。
